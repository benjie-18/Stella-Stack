## D71. The terminal hooks read a `#` inside a word as text, not as a comment (RT22-01; readiness run, 2026-11-08)
- Context: the live test pass on the builder git guard (RT22, requested by the owner) found that `echo x#; git push origin HEAD:main` was allowed and moved `main` in the scratch repos. The five terminal hooks (builder git, model, secret and write guards, and the dispatcher's read-only terminal) split the command with `shlex.shlex(..., posix=True, punctuation_chars=True)`, whose default comment character `#` ends the parse in the middle of a word; bash starts a comment only at the start of a word, so everything after the `#` ran but was invisible to the guard. The same weakness let a secret-file path built with quotes, braces or a glob after a `#` pass the secret guard (the plain owner path was still seen).
- Decision: `lex.commenters = ""` after each of the six constructions (one added line each; no other change to the hooks). The whole command text is scanned, so a real comment that itself names a refused command (`ls # git push origin main`, or `ls # note; rm x` for the read-only terminal) is now refused; bash would have ignored it. ## D72. An empty or malformed owner id fails closed (ultrareview finding 8; 2026-11-08; owner decision)
- Context: D39(4) let any human answer an escalation when `OWNER_DISCORD_USER_ID` was empty or malformed, so the owner could not be locked out. Ultrareview finding 8: a typo or a placeholder then lets any member of the server unblock a card.
- Decision: `bin/escalation-reply-hook.sh` and `bin/escalation-reply-poll.sh` apply a reply or reaction only from a well-formed id that matches. This supersedes the "Empty id" and "Malformed id" sentences of D39(4).
- Limits: with the id empty, the owner cannot answer from Discord until it is set. Nothing is lost: the owner's held reply is applied on the next poll after the fix, and a pending 🔒/🗑️ prompt acts once the owner's reaction counts.
