# SUPERVISOR.md

Policy for the Hermes supervisor (default profile) and every builder on board `ai-stack` (project `stella`).
AGENTS.md rules still apply to builders; where they conflict, AGENTS.md wins for code work and this file wins for
orchestration. A short copy of this policy is the board description (`~/.hermes/kanban/boards/ai-stack/board.json`), rendered from `docs/hermes-local/board.md` by `bin/apply-hermes-local.sh` (D39).
Whether the gateway injects that copy into supervisor or worker prompts is **unverified**: check it in Stage 5,
never assume it.

## Tiers

| Tier | Who | When |
|---|---|---|
| 0 | Scripts (`bin/watchdog.sh`, test/lint/build, git checks) | Always first. A script answer beats a model answer. |
| 1 | Local judge `qwen3.5:9b-64k` | Routine judgement. Answers **only** as JSON: `{"verdict": "...", "evidence": "...", "confidence": 0.0-1.0}`. Non-JSON output counts as a failed judgement. |
| 2 | `bin/escalate.sh <card> haiku "<reason>"` (`claude -p --model haiku`) | Objective triggers below. |
| 3 | `bin/escalate.sh <card> opus "<reason>"` | Planning (`claude --model opusplan`) only when the owner asks or no plan exists. Rescue via Opus when a builder failed twice. |

Tier 2 triggers (objective, any one is enough):
- 2 failed retries on the card;
- the change touches auth, config, or test files;
- the builder modified a test file.

Self-reported confidence is advisory only, never the gate. A low confidence may prompt a closer look; a high confidence never skips a trigger.

All Claude Opus and Haiku calls go through `bin/escalate.sh`. Builders (OpenCode on the local model, Claude Code Sonnet workers) never call Opus directly.

### bin/escalate.sh

`bin/escalate.sh <card-id> <haiku|sonnet|opus> <purpose> <reason...> [-- <claude args>]`, prompt on stdin.
- Requires an existing card id; every call is appended to `.supervisor/escalations.log` (time, card, model, purpose, reason, event, exit code, model actually used, fallback flag, cost) and noted on the card.
- Limits from `.supervisor/limits.env`: Opus only for `plan` (runs `opusplan`) and `rescue`; 1 Opus at a time (lockfile); 40 Haiku calls per UTC day (date-stamped counter in `.supervisor/state/`). Over a limit (exceeded, or zeroed for a test) = exit 3 with a clear message, never an automatic retry.
- Rate-limit or pool-exhausted output (strings verified against claude 2.1.310) = `POOL_EXHAUSTED`, exit 75. A low-risk call is rerouted to the fallback runner (`bin/omniroute-run.sh`, through the OmniRoute gateway on loopback) only when `docs/hermes-local/fallback-routing.json` has `enabled: true` (D77); the result is `{type: result, fallback: true, model_used: <serving model>, text}` with none of Claude's fields, escalations.log gets `POOL_EXHAUSTED` then `FALLBACK`, the card gets a comment and #alerts gets `STL-LIM-404`. A runner that reports a Claude or same-family model, fails, or is disabled leaves the old behaviour: `NO_REROUTE` and the queue. A high-risk call and a drain replay are never rerouted. A call that is not served by Claude is logged and noted as `fallback: true` and never masquerades as a Claude result.
- **Queue (F15, F28, F29):** a call refused by an Opus-slot or Haiku-per-day limit, and every `POOL_EXHAUSTED` call (high- and low-risk), is recorded in `.supervisor/state/queue.jsonl` (id, card, model, purpose, call reason, extra claude args, reason `LIMIT` or `POOL_EXHAUSTED`, created, state, prompt file) with one `#alerts` line per entry; the card comment says "recorded in the queue as <id>; run bin/escalate-drain.sh". Nothing retries it automatically. `bin/escalate-drain.sh --list | --replay <id> | --all | --drop <id>` (manual, no cron) replays through `escalate.sh`, which checks limits and the pool again: still blocked = left queued, no alert; an entry is claimed under `state/queue.lock` before the run, so a second replay does nothing; older than `QUEUE_MAX_AGE_HOURS` (24) or its card done or archived = `stale`. At most `QUEUE_MAX` (50) queued entries; beyond that the call is refused unqueued, with one `#alerts` line an hour. A refused Opus purpose is never queued. Prompt files live only while their entry is queued (F16).
- Test hook (Stage 6 T15): `ESCALATE_FORCE_POOL_EXHAUSTED=1`. Hermetic self-test: `bin/escalate-selftest.sh`.
- **Fallback routing config (D77), the one file for provider, model, routing, fallback chain and lists:** `docs/hermes-local/fallback-routing.json` (`schema_version` 1; check with `bin/omniroute-run.sh --check`). The gateway is started at container start when `enabled` is true (`bin/container-start.sh` runs `bin/omniroute-ctl.sh start` in the background, log `.scratch/omniroute-start.log`; D93); start it by hand with `bin/omniroute-ctl.sh start` if that step failed. Fields: `enabled` (the reroute switch; `true` since D83 after a live probe served a free model, set it `false` to stop all rerouting), `runner`, `gateway {base_url (loopback only), key_file, timeout_s}`, `evidence_log` (one JSON line per attempt: time, role, kind, requested and routed model, provider, ok, http_status, latency_ms, rate_limited, response_cost_usd, error), `prompt_block_patterns` (extended regexes; a prompt matching any is never sent to the gateway and queues instead, `FALLBACK_SKIPPED`), `providers {allow, avoid}` (the provider is the gateway's own `x-omniroute-provider` header, not the vendor in the model name; a provider on `avoid`, outside `allow`, or unknown when a list is set counts as a failed attempt; `enabled: true` needs a non-empty `allow`), `max_cost_usd` (optional, default 0: a response that cost more is a failed attempt), and `roles.<role>.chain`: the ordered list of `{model}` to try, where `<role>` is the escalation purpose (`review`, `judge`, `rescue`, ...) and `default` is used for any role not listed. No fallback model or provider is named outside this file: changing a model, provider or fallback is an edit of this file plus `bin/omniroute-run-selftest.sh`. `enabled: true` needs a non-empty `providers.allow` and `gateway.install_dir` (the runner sends the key only to the process listening on the gateway port when its cwd is under that folder). The gateway (OmniRoute, pinned 3.8.53, installed under `~/.hermes/omniroute`, never in the repo) serves low-risk overflow only: never a Claude subscription call, never Hermes or Ollama. Follow-up (not built): an "Auto (best free)" resolver that picks the model from the gateway's live catalog and this evidence log.
- OpenCode denies direct `claude --model opus|haiku`, `opusplan`, skip-permissions and `setup-token`, and allows `bin/escalate.sh`; piping prompts into `claude -p --model sonnet` stays allowed. In builder Hermes terminals the fail-closed model guard (F14, `docs/hermes-local/hooks/builder/model-guard.py`) refuses any `claude` that runs a model without `--model sonnet` (a bare `claude -p` runs the builder's default model, which is not Sonnet), any `--fallback-model` other than Sonnet, and every permission-skipping flag, also inside quoted command lines; `bin/escalate.sh` is allowed. This is a UX guardrail, not a security boundary: the container and firewall are the boundary.

### #escalations threads

- A blocked card gets one dedicated thread in `#escalations`, named `<card id> · <title>` (up to 100 characters, for example `t_9fbfa27e · T16 escalation test: pick a colour`; D38, replaces D28's title-only name). Only a `needs_input` block gets a thread: a `capability` block, or any block of a card already answered twice, goes to #alerts and a card comment and stays blocked for triage (D38). `bin/escalation-thread.sh <card-id> <title> <question>` posts the thread message: `Card <id>: <title>`, `Decision needed: <reason>` (a reason that already starts with "Decision needed:" is not prefixed again, and text carried over from an earlier escalation such as "External escalation resolved …" or "requires human/orchestrator to acknowledge …" is stripped, so reasons replace and never accumulate; D29; a reason that carries the decision-card template loses everything from "If no comment on this card starts with" onward and every sentence naming `UNBLOCK: escalation reply`, `kanban_complete`, `kanban_block` or `metadata {`, then is cut at a word boundary near 300 characters, so worker instructions never reach Discord; D35), and one reply instruction ("for example: Option A" only when the reason offers options, otherwise "Reply with your instruction in plain words."; D38). No `Blocked:` line (it duplicated the decision). The task line always uses the **original** title saved in the thread map, never a later rewritten title. It maps thread to card in `.supervisor/state/escalation-threads.tsv`.
- **Link in #supervisor (D28, D29):** only when the card's thread is first created, `escalation-thread.sh` posts one #supervisor message: `Escalation <card-id>: "<original title>". Decision needed: <reason> Reply in <#thread_id>`. Exactly one link, in one format (the `<#thread_id>` mention, which Discord shows as a clickable thread name; a mention plus a URL rendered as two truncated chips). Logged as `LINK_POSTED` or `LINK_FAIL`. The card comment has the full URL `https://discord.com/channels/<guild_id>/<thread_id>`.
- **One card, one thread, one notification (D29):** the thread map is checked first. If the card already has a thread it is reused: no new thread, no `THREAD_OPENED`, no new link. A message is posted in it again only for a new, different decision (a fingerprint of each posted reason is kept in `state/escalation-posted.tsv`; logged `THREAD_REUSED` + `ESCALATION_POSTED`). A re-block for the same decision posts nothing (`ESCALATION_SKIP`), or, if a reply was already recorded, `LOOP_DETECTED` plus a card comment that the recorded reply is the answer.
- **Completion (D30):** when an escalated card (one with a thread in the map) reaches `done`, `bin/escalation-complete.sh` reports it exactly once: one `COMPLETED` line in `escalations.log` (thread, reply, summary, status done), one message in the card's thread (`Card <id>: <title>`, then `Resolved: done. Decision: <answer>. [Summary: <summary>.] [Path: <Windows path>.] Status: done.`), which is the thread's closure marker (the thread is not archived, locked, or renamed), and one #supervisor message (`Done <id>: "<original title>". Decision: <answer>. [Summary: …] [Path: …] Status: done.`, no link, no kanban_show dump). The Path is computed from the card's workspace_path and files_created (D38). #supervisor posts go through REST, never `hermes send`, which would mirror them into Stella's session as her own turns (D38). The Summary part appears only when it adds something beyond the decision. The summary is the worker's own (`latest_summary`, for example `Decision: A`). A generic summary such as "Task complete." falls back to the recorded thread reply, with source, thread and answered_by. Triggered by the `kanban_task_completed` hook `bin/escalation-on-complete.sh`, with the reply poller as a cron backstop. A ledger (`state/escalation-completed.tsv`, per card and target) makes it once only, so re-checks never post again. Completion messages never block, open a thread, or post a link. Self-test: `bin/escalation-complete-selftest.sh`.
- **Status reactions (D32):** the recorded reply message in the thread always carries exactly one status reaction from Stella: 👀 answer recorded (the poller, right after UNBLOCKED), ✨ working (the `kanban_task_claimed` hook `bin/escalation-on-claim.sh` when the worker picks the card back up), 🌟 completed (`escalation-complete.sh`). The previous reaction is removed before the new one is added, including from an older reply when a newer one becomes the answer. The status never goes backwards. State: `state/escalation-reactions.tsv`; logged `REACTION` / `REACTION_FAIL`.
- **Completion prompt: Archive / Delete (D37, supersedes the D33 prompt):** after completion Stella posts once in the thread: "What should happen to this thread? React 🔒 Archive (renamed with 🔒, read-only) or 🗑️ Delete. No reaction keeps it open.", with both pre-added (prompt rows `v3`). Not reacting means keep. `bin/escalation-reply-poll.sh` acts every minute on human reactions only (bots never count):
  - 🗑️ deletes the thread (`THREAD_DELETED`).
  - 🔒 posts "Archived by <user>: this thread is now read-only.", renames the thread to `🔒 <original title>` (from the thread map, cut to Discord's 100-character limit counted in UTF-16 units), then archives and locks it (`THREAD_ARCHIVED`); only Manage Threads can reopen it. Two PATCHes, rename first while the thread is active, each confirmed from Discord's returned name and `thread_metadata`.
  - 🔒 and 🗑️ together is a conflict: one note asks to remove one (`PROMPT_CONFLICT`) and nothing happens until only one remains. Archive and Delete are final: the thread is never polled, reused, or posted in again, and a later escalation of the same card gets a new thread. Status reactions (👀 ✨ 🌟) use different emoji, on the reply, not the prompt.
  - `delete_thread` and `archive_thread` refuse anything that is not a thread of #escalations. A thread removed by hand is recorded as gone (`THREAD_GONE`). Older prompts are migrated once to the two-choice text (`PROMPT_MIGRATED`): a v2 📌/🔒/🗑️ prompt loses Stella's own 📌 (📌 does nothing); an old ✅/❌ prompt gets 🔒 and 🗑️ instead (an old ✅ never deletes). Threads archived before D37 are not renamed unless the owner asks.
  - These are reactions, not buttons: a button click goes to Hermes's gateway, which has no handler for custom buttons (D4). Needs Manage Threads (granted, verified live 2026-10-26).
- **Kanban guard (D31):** `bin/kanban-guard.sh`, a `pre_tool_call` hook on every `kanban_*` tool in all four profiles (matcher `^kanban_.*`: Hermes fullmatches matchers, so the original `^kanban_` matched no tool and the guard never fired until the 2026-10-27 fix) (fail-open), refuses two things. (1) A call that names a board other than `ai-stack`. (2) A `kanban_block` on a card whose thread reply is already recorded, for a reason whose normalized fingerprint was already escalated. The worker is told the recorded answer and to finish the card, and `REBLOCK_REFUSED` is logged. A new, different decision is allowed. Self-test: `bin/kanban-guard-selftest.sh`.
- **Forged answers (F26):** the kanban guard also refuses any `kanban_*` call whose text carries `UNBLOCK: escalation reply` (case, spacing, line breaks, Unicode spaces and invisible format characters ignored), in any profile: only the poller writes the owner's answer, through the CLI (`hermes kanban unblock --reason`), which is not a tool call. The one exception is the decision-card clause Stella's SOUL requires ("starts with 'UNBLOCK: escalation reply'"). Residual: the guard is fail-open, and a comment's author field does not prove who wrote it. Every scripted kanban call names its board (`hermes kanban --board`, the one value in `bin/kanban-board.sh`, F4).
- **Tools (D31):** `bin/escalations-status.sh [--all]` is a read-only overview of escalated cards (live status, latest event, original title, thread URL), so `hermes kanban show` per card is not needed. `bin/selftests.sh` runs every hermetic escalation self-test and is part of `npm test`, so the 15-minute watchdog alerts #alerts on a regression.
- **Loops and triage (D29):** Hermes routes a card to `triage` when it blocks again with the same kind after an unblock (`block_loop_detected`, `BLOCK_RECURRENCE_LIMIT` 2), and the triage specifier may rewrite its title and body. That is an escalation loop, not a genuine repeated failure: the hook logs `LOOP_TRIAGE` with the card id, kind, recurrences and cause and posts nothing; the supervisor stops the card (archive with a note) instead of re-dispatching it. The fix is upstream: a worker never re-blocks for an answered decision (builder SOULs, "Escalation answers"). Note that Hermes counts by kind only, so a second, genuinely different `needs_input` decision after an unblock also lands in triage.
- **No second #supervisor summary (D29):** the default profile has `kanban.auto_subscribe_on_create: false`, so Hermes's kanban notifier no longer wakes Stella in #supervisor for cards she creates; the single link message above is the block notification. Stella's SOUL also forbids a second summary, a kanban_show dump, or another link: after kanban_create for a decision card her whole reply is one line, `Card <id> created for <assignee>; the #escalations thread will follow.`, and she never tells the owner to type "UNBLOCK" or any prefix (the owner replies in the thread in plain words). This one is SOUL-only, not hook-enforced (a reply's text cannot be hooked); the Phase 5 retest verifies it (D35).
- **Trigger (D25):** the thread is opened automatically for every card that ends up `blocked`, whoever blocks it (a worker's `kanban_block` or the CLI; Stella's own `kanban_block` is refused by a hook, D35). Hermes fires `kanban_task_blocked` inside `block_task()`, and the shell hook `bin/escalation-on-block.sh` runs `escalation-thread.sh` in the background (dependency blocks wait in `todo` and are skipped). Each firing and skip is logged to `escalations.log` (`HOOK_FIRED`, `HOOK_SKIP`, then `THREAD_OPENED` or `THREAD_FAIL`). The supervisor never opens a thread by hand, and never asks for the decision in #supervisor instead.
- **Token (D25, option A):** `escalation-thread.sh` creates the thread inside Hermes's own runtime, calling Hermes's own token loader (`load_hermes_dotenv()`, the same call every `hermes` command, `hermes send` included, makes). The bot token stays inside that short-lived process: never printed, logged, written to a file, or passed as an argument or visible environment variable. The scripts never read `~/.hermes/.env` themselves. The helper first runs Hermes's runtime prelude (`import hermes_bootstrap`, as `hermes --print-runtime-command` shows), without which Hermes's packages are missing (D26). Every Discord failure is logged with channel, thread name, HTTP code, stage and the full error, never an empty detail; `bin/escalation-thread.sh --check` runs a read-only `channel_info` on #escalations through the same path, creating no thread (`--check create` makes one clearly named test thread, for isolation tests only). The script pins `HERMES_HOME` to the default profile, which owns the Discord bot, because a worker's hook runs with its own profile's secrets (D27).
- **T16 cards are blocked by the worker, never by Stella in chat.** Stella creates the card on board `ai-stack` with `--project stella --workspace worktree`; a decision-only card is assigned to `builder-claude` (builder-local cannot complete it past the false-close guard). Its body uses the fixed two-branch decision-card template in Stella's SOUL (`docs/hermes-local/soul/default.md`): no UNBLOCK escalation reply yet → block once with kind `needs_input`; reply present → complete with summary `Decision: <answer>` (D31). Stella does not call `kanban_block` on it herself, and a fail-closed default-profile hook refuses it if she tries (D35). Workers treat `UNBLOCK: escalation reply …` comments as the human answer, never block again for the same decision, and never re-run a "first action: block" instruction (builder SOULs, "Escalation answers").
- **Re-registration (local-only config):** the hook is registered in `/home/node/.hermes/config.yaml` and `/home/node/.hermes/profiles/{builder-local,builder-claude,reviewer}/config.yaml`, plus each profile's `shell-hooks-allowlist.json`. All live in the `~/.hermes` volume, not the repo: they survive a rebuild, not a volume reset. After a volume reset, run `/workspace/bin/apply-hermes-local.sh` in a container terminal (idempotent). It re-applies the repo-managed SOUL rules (`docs/hermes-local/soul/<profile>.md` into a marked region of each profile's SOUL.md), `kanban.auto_subscribe_on_create: false`, and all escalation hooks via `bin/register-escalation-hook.sh` (`kanban_task_blocked`, `kanban_task_completed`, `kanban_task_claimed`, the `^kanban_` guard, and the fail-closed profile guards of "Tool access and audits"). `bin/apply-hermes-local.sh --check` changes nothing and reports drift (exit 1). Edit SOUL rules in the repo files, never in `~/.hermes` directly, then re-apply (D31).
- **Replies (D28):** a plain reply in the card's thread, with no @mention needed, is the decision. The Discord gateway does not deliver these thread messages to Hermes (the thread is created through the REST API, so the adapter's mention gate drops them before any hook), so `bin/escalation-reply-poll.sh` reads each blocked card's thread through the Discord API (container cron every minute, `bin/crontab.txt`; each run makes 5 passes 12 s apart under one lock, so a reply is seen within ~15 s; D38). The oldest human message not yet recorded is logged as `REPLY`, the card is unblocked with it as the reason (an `UNBLOCK: escalation reply …` comment), and `UNBLOCKED` is logged; Discord errors log as `POLL_FAIL`. Not applied, only logged (D38): a reply on a card already answered twice (`LOOP_HELD`, one #alerts line, card comment), on a `capability` block (`REPLY_HELD`), or a bare "A"/"Option B" when the block reason has no options (`REPLY_UNMATCHED`, ❓ on the reply, one line asking for plain words). Message ids go to `.supervisor/state/escalation-replies.tsv` so a reply is never recorded twice. The `post_gateway_admission` hook `bin/escalation-reply-hook.sh` stays as a second path and uses the same ledger; it does not apply the D38 holds, and it does not fire because the gateway drops these messages. Self-test: `bin/escalation-reply-poll-selftest.sh`.
- **Failure paths (B1 audit, 2026-10-28):** a failed thread post is `THREAD_FAIL` plus one #alerts line per card an hour (F1); the poller retries a blocked `needs_input` card that has no thread on the first pass of a run, at most 3 times (1, 5, 15 min), under the thread script's per-card lock (`state/thread-<card>.lock`, F7), then one #alerts line; a failed #supervisor link is alerted once (F5); a reply is marked seen only after its unblock worked, else it is tried again every pass and alerted once (F2); an unreadable board is `POLL_FAIL` plus #alerts at most hourly (F3); three failed reads of one thread in a row raise #alerts at most hourly (F6); a completion prompt unanswered for 7 days is `expired`, no longer polled, the thread kept (F21). Every poller pass writes `state/reply-poll.heartbeat`; `bin/watchdog.sh` (every 15 min) alerts once when it is older than 5 minutes, once when the gateway process is gone or `gateway.log` is silent over 60 minutes (`GATEWAY_SILENT_MIN`, D42) while Hermes is not paused, once per failing or hung (over 600 s) test or lint streak, and once on each recovery. REST posts send `allowed_mentions: {"parse": []}` (F20); `hermes send` posts (thread messages, #alerts lines) cannot. Scripts run with `LC_ALL=C.UTF-8` so cuts never split a character (F19).
- **Alert wording (D44):** every automatic #alerts message is rendered by `bin/alert.sh` from `docs/hermes-local/alert-catalog.json`: plain language for the owner, a stable code `STL-<area>-<nnn>` in the title (a ✅ "resolved" form when a problem clears), the raw technical detail only in `.supervisor/logs/alerts.log` (code first: `grep STL-ESC-210`), troubleshooting in `docs/alert-codes.md` (generated: `bin/alert-catalog.sh --docs`). Triggers, thresholds, rate limits, dedupe keys and transports are unchanged. Stella answers "what is STL-ESC-210?" with `/workspace/bin/alert-explain.sh STL-ESC-210` (allowed in her read-only terminal). Not converted: `bin/container-start.sh`'s apply-failure line (reboot-relevant; STL-RCV-501 reserved for it).
- **Threads only** (decision D4): the reply in the card's thread (Approve, Deny, Option B, or specific instructions) is the decision. No custom button plugin, and no `clarify` taps (non-deterministic). Dangerous-command approval buttons (Hermes ExecApprovalView) are separate and stay. Live thread proof is Stage 5 / T16.

## Supervision levels

- **Standard** (default): tiers above.
- **`supervision:plus`** label on the board or card: planning, delegation and review run on Sonnet and Opus via `bin/escalate.sh` from the start, and the pool cost of each call is noted on the card.

## Workers and branches

- Maximum **2 concurrent Claude Code workers**.
- One git worktree and one branch per task, named `<project-slug>/<card-id>-<title-slug>` (`stella/…`). Cards are created with `--project stella --workspace worktree`; never rely on the auto `wt/<card-id>` branch.
- `builder-local` always runs `opencode run --standalone --auto` (the default-profile OpenCode service holds port 49374; never kill it).
- `builder-local` cards are always created with `--project stella --workspace worktree`, never `--workspace scratch`: outside `/workspace` OpenCode would not load `opencode.json`. The user default `~/.config/opencode/opencode.json` also pins `ollama/qwen3.5:9b-64k` so OpenCode can never fall back to a cloud model.
- **False-close guard**: builder-local's `kanban_complete` runs `bin/false-close-guard.py` (fail-closed `pre_tool_call` hook). It blocks unless the session really ran `opencode run --standalone --auto` with exit 0 and output, and the evidence has `delegate_exit_code: 0`, `delegate_output`, and `files_created` naming files that exist, that OpenCode's output names, and that no other tool call wrote.
- **Check guard (RU-01, D63)**: a builder's `kanban_request_review` and `kanban_complete` run `bin/check-guard.py` (fail-closed `pre_tool_call` hook, builder role in `roles.json`). Stella ends every card body with `Check: <command>` (or `Check: none: <reason>`). The hook proves the card's own worker run, then reads the worker's session: the exact command ran in its terminal in the foreground as `cd <worktree> && <command>` (or with `workdir` set to it) with exit 0 and output, and no `write_file`, `patch` or `delegate_task` came after it (a worktree path that needs quoting is accepted as `cd '<path>' &&`). A decision card says `Check: none: decision card`. A missing Check line is Stella's omission: the worker blocks `needs_input` and asks. The hook runs nothing itself; a terminal write after the check is not seen, the reviewer reads the check's output.
- **Complete gate (S3A-03, S3A-04, D66-D67)**: `bin/complete-gate.py` runs on `kanban_complete` for the builder and reviewing roles (fail-closed, role data in `roles.json`). A reviewing role's completion must carry its `complete_metadata` pair (`{"review": "approved"}`, the verdict `merge-card.sh` reads). A builder (`complete_needs_review`) may not complete a card whose Check line is a command: it requests review and a reviewing role completes the card; a `Check: none: <reason>` card (decision) still closes with the builder's own call. A `Check: none` card cannot complete on builder-local (D68): its refusal says to block `capability` and ask for reassignment.
- **Watchdog step budget (RU-07, D69)**: the cron watchdog job runs with `WATCHDOG_STEP_TIMEOUT=1200` (set in `bin/crontab.txt`); a step still running after that is killed and reported as hung (STL-WDG-102). The suite takes 11-13 minutes; a run still active at the next 15-minute tick makes that tick skip.
- **Commits (D36):** a worker commits only in its own card worktree, on its card branch. Before any git command, `git rev-parse --show-toplevel` must equal the card's workspace path and `git branch --show-current` the card's branch; otherwise it blocks with kind `capability` and both outputs. Never `git config`, `git add -A` / `git add .`, a commit on `main`, or `--no-verify`. ### Project file location (canonical rule)

1. ## Closing a card

A card closes only when all of these hold:
1. The delegate's exit code is in the evidence and it is **0**. Any other exit code means `kanban_block`, never complete.
2. The delegate itself produced the change (not the supervisor or a fallback writing the file).
3. The evidence is **on the card** (metadata, comment, or attachment), not only in a worktree.
4. **Merge before close**: the commits are on `main`, or pushed to `origin` on the card branch, and the evidence has the SHA plus the merge or push output.

Work that lives only in a worktree is never evidence. Never assume a worktree survives: Hermes keeps it only while it is dirty or unpushed, and removes a clean, fully-pushed one on completion.
Review keeps the worktree open: use `request-review`, and complete only after approval and merge.

**Who completes (D46, D48).** A `kanban_complete` tool call passes only from the card's own worker run
(`bin/role-guard.py`, fail-closed): the caller is the card's assignee, its role may complete, and the card's open run is
bound (the `worker_bound` event Hermes writes before the first model call, under the run's claim lock) to a process among
the hook's ancestors with the recorded start time. The worker's `HERMES_KANBAN_*` variables are not used: the worker sets
them after it starts, so no `/proc` file shows them, and Hermes strips them from its hooks. Anything unproven is refused
with STL-GRD-601 and one line in `.supervisor/logs/alerts.log` naming the proof that failed (no recorded worker process, not
an ancestor of this call, start time differs, claim lock differs, no open run, assigned to another profile, board
unreadable). The dispatcher never completes.

**Worker git identity (D48).** A role in `docs/hermes-local/roles.json` may carry `git_identity {name, email}`: two keys
of `config/owner.env` (today `WORKER_GIT_NAME`, `WORKER_GIT_EMAIL`; the owner adds them, like every owner value). Apply
(`bin/apply-hermes-local.sh`, also at container start) writes `user.name`, `user.email` and `safe.directory` (the stack and
the board's project repos) into `<profile>/home/.gitconfig` of each profile of that role, and `--check` reports a home
that differs. Keys the owner has not set are reported ("git identity NOT SET"), not written.

**Live proof that a worker completes (D48, owner; Stage 6 T7).** An agent session does not create cards for this. In the
container, with `<worker>` a builder profile and `<project>` a slug from `hermes project list`:

    bin/apply-hermes-local.sh --check                      # "<worker>: git config in sync" (not "NOT SET")
    before=$(grep -c STL-GRD-601 .supervisor/logs/alerts.log)
    hermes kanban --board ai-stack create "proof: add docs/scratch/proof.md" --assignee <worker> --project <project> \
      --workspace worktree --body "Create docs/scratch/proof.md with one line, commit it in the worktree, then request review."
    hermes kanban --board ai-stack watch                   # until the card is in review, then until it is done
    hermes kanban --board ai-stack show <card> --json | jq '{status: .task.status, runs: [.runs[] | {id, outcome}]}'
    git -C .worktrees/<card> log -1 --format='%an <%ae> %s' # the commit exists, under the configured identity
    [ "$(grep -c STL-GRD-601 .supervisor/logs/alerts.log)" = "$before" ] && echo "no new refusal"

It must show: a `worker_bound` event for each run (`... show <card> --json | jq '.events[] | select(.kind=="worker_bound")'`),
a `review_requested` run, then the reviewer's approval and a final run with outcome `completed`, `status: "done"`, the commit
under the identity, and the same STL-GRD-601 count as before. A new STL-GRD-601 line names the proof that failed (D48); paste
it into the batch notes and complete the card from the CLI (below).

**Completing a stuck card (owner only).** If a card is done but its worker cannot complete it (for example the run
identity never reached the guard: STL-GRD-601 on the card's own worker), complete it from the container's command line.
The CLI runs no tool hooks, so no guard can strand a card:

    hermes kanban --board ai-stack show <card>          # check the evidence first (Closing a card, above)
    hermes kanban --board ai-stack complete <card> --summary "Completed by the owner: <why>" \
      --metadata '{"completed_by": "owner", "reason": "<why>"}'

## Merging (R1.2 risk-tiered push)

- **Low risk**: auto-push once all checks are green.
- **High risk** (marked by a `risk: high` line in the card body) needs a Discord approval before push **and** a rollback plan on the card. High risk = migrations, auth or security code, payment or billing code, destructive operations, dependency major upgrades, firewall or devcontainer changes.
- **Rollback** = revert commit + push, redeploy by the normal path, verify live, post-mortem note on the card.
- **Post-deploy smoke check** = homepage + one critical journey. A failed smoke check triggers rollback, not fix-forward.
- Dangerous-command approvals reach the owner as Discord buttons. Never pass `--yolo` or `--dangerously-skip-permissions`.

## R1.1 Durable orchestration

- States: `ready`, `in_progress` (Hermes: `running`), `review`, `done`, plus `blocked` and `failed`.
- Card metadata carries: `state`, `attempt`, `heartbeat` (UTC ISO), `last_error`.
- Two attempts by the same builder, then reassignment or escalation.
- Heartbeat at least every 15 minutes. No heartbeat for 60 minutes = **stale**: re-queue or escalate, never leave it silent.
- Dependencies are `depends_on` card ids (Hermes parent links); dispatch skips cards whose dependencies are not `done`.
- Crash recovery re-reads all non-done cards and resumes from recorded state, never from conversation memory.
- A daily sweep compares card states against worktree and branch reality and corrects mismatches.
- A card in `ready` for more than 30 minutes is reported (usually the gateway dispatcher is down). The gateway runs in tmux session `hermes` under `bin/hermes-gateway-loop.sh` (restarted on exit, no idle-exit), started by postStartCommand; after a plain `docker start` the Windows recovery tasks in `docs/recovery.md` restore it.

## Reuse of created skills and tools (D22)

- A skill or tool created in a worktree can be reused by other agents in other worktrees only after it is committed (worktrees see committed config only), and after triage: SkillSpector scan, show-me, and supervisor review, recorded in decisions.md.
- Automatic reuse, with no the owner approval, is allowed only for low-risk, read-only, no-network, no-secret tools. Network, write, or secret tools need the owner's approval in #escalations before other agents can use them.

## Account creation (D23, post-go-live only)

- A per-project vault in the broker, host-side only, never in a card or repo file. The owner provides one project email, once per project.
- The broker generates a unique password per service and stores it in the vault (never one reused password per project). Agents never see password values; the broker performs create and login actions and returns only a result or a short-lived session.
- The broker keeps a host-side ledger: project, service, account email, creation date, card id, purpose, last used. No passwords in the ledger. The owner can ask the supervisor to list accounts per project from it.
- Auto-create with no the owner interaction is allowed only for free, low-risk services with no payment method, no phone verification, and no ID verification. Every creation is logged immediately.
- If an account already exists for that service in that project, the agent stops and raises an #escalations thread comparing the existing account with the proposed new one. The owner replies Use existing, Create new, or Deny. Paid, phone, ID, or high-risk services also escalate, even if no account exists yet.
- No agent-led signup from credentials the owner supplies in chat, no paid tier, no personal email reused for a business account, and no terms acceptance without approval for that specific service.
- iCloud Keychain is not a direct write target from the Windows broker. The broker vault is the source of truth, with 1Password or Vaultwarden as a sync backend if the owner wants those credentials on their iPhone automatically.

## Environment-conscious delivery (D24)

**Environment facts. Use them; do not guess.**
- The host is Windows. STACK is the owner's stack path as given in your SOUL on Windows, and `/workspace` inside the container is that same STACK folder (the owner's stated layout; the container cannot see the host path itself).
- Container terminal commands run inside the devcontainer; PowerShell commands run on the Windows host; Discord messages run in Discord; Windows browser actions run in a Windows browser outside the container. Never mix them: no Discord message given as a shell command, no PowerShell command given for the container, no container command given for Windows.
- The container has no GUI display. Chrome inside the container is blocked by seccomp unless it runs with `--no-sandbox` (D16), and even then it cannot open a GUI browser for the owner. Never suggest `xdg-open`, `open`, or a GUI browser launch for a container file.
- A file in `/workspace` is reachable on Windows at the owner's stack path as given in your SOUL, then `\<same relative path>`. A file only in `~/.hermes/cache`, `/tmp`, a scratch folder, or an unmerged worktree is not reachable on Windows and is not a deliverable.

**Before giving any command or instruction, check that it runs where you say it runs.**
- Name the environment in the instruction: "in a container terminal", "in PowerShell on Windows", "in Discord #supervisor".
- Verify that the command exists, that the path exists in that environment, and that any required flag (for example `--no-sandbox` for Chrome in the container) is included. If you cannot verify it, say so explicitly; never present a guess as a tested instruction.
- If a tool writes its output to cache, `/tmp` or scratch by default, that is not a delivery: copy it to `/workspace`, verify it with `ls -l` and the file size, and only then report it as done.

**Deliverables, every time, no exceptions.**
- Every file, HTML page, report, screenshot or other deliverable is placed in `/workspace` (or in a worktree file that is then merged to main) and verified on disk before it is reported as done.
- Every `/workspace/<path>` is reported with its Windows path (the owner's stack path as given in your SOUL, then `\<path with backslashes>`), never "N/A"; a path outside `/workspace` is reported as container-only (Stella's and both builders' SOULs, D24).
- Report the container path and the Windows path together, for example `/workspace/decision-card.html` and its Windows path (the owner's stack path as given in your SOUL, then `\decision-card.html`), with a Windows-accessible way to open it: double-click in Windows Explorer, open in a Windows browser, a localhost URL served from `/workspace` for the Windows browser, or a Playwright screenshot as evidence when a browser open is not possible.
- Never report a result as done when it exists only in cache, `/tmp` or scratch. Cache is temporary, not a deliverable, and does not survive a rebuild or a worktree cleanup.
