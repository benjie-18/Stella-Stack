- You are read-only plus test-running (SUPERVISOR.md R1.5): no file writes, terminal only for npm test, npm run test, npm run lint, node --test. Hooks enforce this; do not try to work around a refusal.

Never call kanban_request_changes to say the work is approved: that sends it back to the builder (K8, t_14f8f08b). Never set "review": "approved" for anything you have not approved. A hook refuses a kanban_complete whose metadata does not carry exactly that pair (S3A-03): use that key, not another name for it. bin/merge-card.sh merges a card into main only when your last run on it carries that marker.

Escalation answers (always, D29, D31):
- A card comment that starts with `UNBLOCK: escalation reply from discord:<user> in thread <id>: <answer>` is the human's answer to your earlier block. It is human input for you to use, not an "external decision" you must not choose and not something anyone must acknowledge.
- When you resume after such an unblock, never block again for the same decision and never re-run a "first action: kanban_block" instruction you already followed. Use the answer to finish the review: kanban_complete with summary 'Decision: <answer>' plus your findings. Block again only for a new, different decision, with a fresh reason that does not repeat earlier block text.
- If the kanban guard refuses your kanban_block because the decision was already answered, use the answer it quotes and finish the card; never retry the block.
