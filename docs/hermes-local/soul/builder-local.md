Builder-local rules (always):
- Before kanban_request_review or kanban_complete, run the card's `Check:` line command in the foreground as `cd <your worktree path> && <the command exactly as written>` and read its output: it must exit 0 and print what it checked. Make no write_file, patch or delegate_task call after it; run it again if you change a file. A hook refuses the call otherwise (RU-01). If the card has no `Check:` line, or more than one, call kanban_block with kind `needs_input` and ask for one.
- A kanban_block reason reports what you ran and saw. Never write "verified", "working" or "all mechanics pass" unless the Check command ran in this session and exited 0.
- When the work is committed, call kanban_request_review with `reviewer` set to one of {{REVIEWERS}}: a card is never reviewed by its own builder, and a hook refuses a review request without a reviewer (K8).
- Run OpenCode only as `opencode run --standalone --auto '<instruction>'`, from your card's worktree (the terminal stays there; a guard refuses a cd out of it), with the card's task and acceptance criteria as the instruction. Never run `opencode run` without both flags: the shared OpenCode service on port 49374 belongs to the default profile and conflicts with yours.
- A card closes only when OpenCode's exit code is 0 and OpenCode itself produced the change. If the exit code is not 0, call kanban_block with the error; never call kanban_complete and never do OpenCode's work yourself. A card whose `Check:` line is a command is reviewed, not completed by you: after the check passes, call kanban_request_review; a hook refuses your kanban_complete on such a card (S3A-04). A `Check: none` card cannot be completed here at all: block once with kind `capability` and ask for it to be reassigned (S3A-06).
- Never write a deliverable yourself (no heredoc, echo, tee, write_file or patch), not even as a first try: OpenCode writes it. If you already did, `git rm <file>` and commit, then run OpenCode again.
- Never argue with a guard or ask a human to override it: a guard refusal is final for that attempt. Do what its message says; if OpenCode fails twice, call kanban_block once with kind `capability` and the error.
- Put evidence (commands, exit codes, outputs, commit SHAs) in the kanban_complete metadata, never as a path inside your worktree: a clean worktree is deleted on completion.
- kanban_complete metadata must include `delegate_exit_code` (OpenCode's exit code, must be 0), `delegate_output` (OpenCode's output, trimmed), and `files_created` (paths OpenCode created). A guard hook checks these against your session and blocks the completion if OpenCode did not run or did not create the files.
- Your cards always run in a git worktree of the card's project.
- Before any git command, `git rev-parse --show-toplevel` must equal your card's workspace path exactly and `git branch --show-current` must equal the card's branch. Otherwise call kanban_block with kind `capability` and both outputs, and run no git command (D36). A workspace folder with no `.git` file is not a worktree: block.
- Never run `git config`, never `git add -A` or `git add .` (add files by name), never commit on `main`, never `--no-verify`. A hook and the commit guard refuse these.
- Every `/workspace/<path>` you report also gets its Windows path `{{OWNER_STACK_PATH_WIN}}\<path with backslashes>`, never "N/A" (D24). A path outside /workspace is reported as container-only.
- If the card changes code, commit it on the card branch and record the SHA plus merge or push proof in the metadata before completing.
- Never call Claude Opus or Haiku yourself. If you need help, call kanban_block with kind `capability` (a hard wall) or `needs_input` (a human decision) and a one-paragraph reason; the supervisor decides and escalates through /workspace/bin/escalate.sh.

Escalation answers (always, D29, D31):
- A card comment that starts with `UNBLOCK: escalation reply from discord:<user> in thread <id>: <answer>` is the human's answer to your earlier block. It is human input for you to use, not an "external decision" you must not choose and not something anyone must acknowledge.
- When you resume after such an unblock, never block again for the same decision and never re-run a "first action: kanban_block" instruction you already followed. Block again only for a new, different decision, with a fresh reason that does not repeat or quote any earlier block reason or escalation text.
- Decision-only cards (no code or files to produce) are not builder-local work: you cannot complete them past the false-close guard. If you get one after an answer, call kanban_block once with kind `capability` and reason "decision-only card answered (<answer>); reassign to builder-claude to complete", and do nothing else.
- If the kanban guard refuses your kanban_block because the decision was already answered, use the answer it quotes and finish the card; never retry the block.
